# Installed FPMessageAttr construction and kernel random registration

The installed FairPlayIOKit caller uses the nonzero payload from its selector 26 schema lookup to construct a separate 112 B `site.FPMessageAttr`. Both successful modes request 64 kernel random words. Payload byte +4 controls whether the caller replaces the first generated 32 B with cached bytes or keeps the generated bytes and sets a flag. The caller copies the same cached 16 B and header in both modes. An allocation failure takes a separate status path. [Installed lookup result](live_fairplay_schema_lookup_result_report.md) [Auditor](triage_evidence/audit_live_fairplay_message_attributes.py) [Replay receipt](triage_evidence/live_fairplay_message_attributes_audit.json.zst)

The same installed collection shows how corecrypto startup supplies the two callbacks used by `_random`. Kernel registration writes the context and both signed callbacks into the exact cells consumed by the wrapper. All three cells contain zero in the file and have no chained fixups. The binding follows from the registration instructions. Native startup and runtime cell values remain unknown.

```text
occupied lookup -> payload P -> typed FPMessageAttr request
  |-- null allocation -> workspace error -> cleanup transfer
  `-- allocated A
       |-- _random x32 -> A+08
       |-- _random x32 -> A+28
       `-- copy cached16 -> read mode at P+04
            |-- zero    -> replace first generated field with cached32 --+
            `-- nonzero -> retain generated field and set flag ---------+
                                                                       |
                                                             copy header -> continue
```

## Kernel random and corecrypto

The `_random` wrapper occupies 116 B. Four instruction words differ from the original capture because the callback and context references relocated. The wrapper first requests refresh, then reloads the context and requests four bytes at its local SP+0xc. It returns the resulting u32 AND `0x7fffffff`. The retained constructor proof and installed replay give `low8(provider_word) XOR 0xc7` for the stored byte under this interface. Both loops run even when the caller later replaces the first 32 B. The replay supplies deterministic provider-word fixtures, including the mask boundaries. [Historical wrapper and byte proofs](userclient_message_attributes_report.md)

## Verification and assumptions

The audit pins the collection SHA-256 and embedded UUIDs, checks 487 kext words in 19 spans, verifies two pool-address relocations and resolves 115 continuation slots. Eight bank arrays match their archived bytes, and four selector rules each pass all 256 inputs. The two scalar fixtures each run all three attribute profiles. Their six suffixes cover 11,890 instruction visits, 564 stores and 576 transfers, including six allocator returns and 256 random returns supplied by the model. The audit reproduces all 199 archived UNSAT partitions. The constructor and copies have O(1) time and space with respect to P's extent, excluding provider and allocator internals.

The concrete runs replace volatile registers at each modeled return. Native callee effects would require separate observation. |
