# AES descriptor binding and DMA prepared-range contract

The nominal AppleS8000 AES path binds descriptors through `IODMACommand::setMemoryDescriptor`. A fresh nonnull binding with prepare=true requests `prepare(0,0,true,true)`; its zero length selects the descriptor-summary length. The segment wrapper subsequently checks cursors against that prepared range. The selected descriptor operations 1 and 2 take a barrier-only source path, with no offset/length inspection. These results refine the earlier no-effect API fixtures; they do not establish a native mapping, actual descriptor extent, hardware submission or completion. [DP1-DP8]

```text
outer AES command: descriptors, offsets, progress, quantum
  -> each inner-job DMA adapter: setMemoryDescriptor(descriptor,true)
       same descriptor -> immediate raw success; no new prepare
       fresh descriptor -> 32 B descriptor summary -> retain/publication
         -> prepare(offset=0,length=0,true,true)
              zero length -> summary length -> prepared offset/length
  -> descriptor performOperation(2 or 1,offset,quantum)
       flag bit 18 clear -> DSB SY -> raw success
  -> configuration frontier [not joined through its body]

separate transfer consumer -> genIOVMSegments(cursor*,record*,count*)
  -> prepared-state/cursor gate -> mapping/segment walk [partial contract]
  -> transfer count = min(remaining,segment_A.length,segment_B.length)
  -> register-access frontier [not executed]
```

Primary evidence is the [original-source certificate](triage_evidence/aes_dma_preparation_checks.json.zst), generated by [source extraction and lifting](triage_evidence/recover_aes_dma_preparation.py) and checked by an [independent publication audit](triage_evidence/verify_aes_dma_preparation_publication.py). It extends the [provider admission](aes_provider_admission_report.md), [quantum binding](aes_quantum_binding_report.md) and [buffer lifecycle](kext_buffer_report.md) reports. All offsets and extents are bytes; addresses are original unslid virtual addresses.

## Binding, descriptor summary and prepare request

Let D be a DMA adapter, M the incoming descriptor, and R=u64[D+0x70]. Binding compares M with u64[D+0x48]. For the same descriptor and prepare=true, `0xfffffe000c5289a8` branches directly to raw success at `0xfffffe000c528bf0`; this shortcut does not refresh the summary or prepared state. A different descriptor with an old nonnull binding and nonzero u32[D+0x68] instead returns `0xe00002d5`. An inactive old binding is cleared before proceeding. NULL incoming descriptors do not enter the fresh-summary path. [DP3,DP4]

For a fresh nonnull descriptor, source clears 32 B at R+0x40 and calls M's +0x150 at `0xfffffe000c528a78`. The request code is `0x02000001` when `(u32[D+0x64]&15)==0`, otherwise `0x02000000`; the output pointer is R+0x40 and the supplied size is 32 B. A nonzero summary result returns directly before publishing the new descriptor. [DP3,DP4]

The descriptor's original dispatcher selects this summary group and requires supplied size >=32 B. Its initial writes and direction leaf establish the following exact data flow; unspecified fields and deeper conditional branches remain unproved:

| Summary offset | Width | Source |
| --- | --- | --- |
| +0x00 | u64 | u64[M+0x50], also returned by the length getter |
| +0x08 | u32 | u32[M+0x68] |
| +0x0c | u32 | u32[M+0x98] |
| +0x14 | u32 | u32[M+0x9c], only on the nonzero u32[M+0x88] branch after the direction call |
| +0x18 | u32 | `u32[M+0x20]&7` through nominal getDirection |

After a successful summary, binding publishes M to D+0x48 at `0xfffffe000c528ae8`, requests retain, and conditionally releases the previous pointer. For prepare=true it calls D's +0x160 at `0xfffffe000c528bb0` with `(offset64=0,length64=0,bool=true,bool=true)`. A nonzero prepare result requests `clearMemoryDescriptor(true)` at `0xfffffe000c528be4` and then restores the saved prepare result; that return is distinct from cleanup's result. Reference effects, drainage of complete calls and actual preparation remain conditional. [DP2-DP5]

## Prepared extent and selected cache-operation semantics

`prepare` starts with raw status `0xe00002d8` and requires the callback field D+0x50 to be nonnull. If incoming length is zero, `0xfffffe000c5281d8` loads u64[R+0x40]. The effective length is compared unsigned with u64[D+0x30]; exceeding it selects `0xe00002db`.

The source increments u32[D+0x68] modulo 2^32 before distinguishing repeated and first preparation. Repeated preparation requires saved offset and length equality for raw success. On the first-preparation arm, the effective length must have no bits selected by zero_extend64(u32[D+0x38]). A further check reads the **previous** R+0x68 field and tests its upper 18 bits (`>>46`), before overwriting that field; it is not a proved bound on the new requested length. The admitted publication at `0xfffffe000c528244` stores incoming offset at R+0x60 and effective length at R+0x68, and clears selected auxiliary fields. Later mapper/configuration work can still fail. [DP3-DP5]

Thus, under DP2-DP5 and a successful fresh preparation in one stable epoch:

```text
prepared_offset = 0
prepared_length = summary_length = u64[descriptor+0x50]
```

The outer AES quantum and remaining count are separate command fields. The buffer factory requests 81920 B in earlier evidence; this increment does not prove that its native descriptor length, the prepared range and a particular outer AES request share one constructor/runtime epoch. [DP5]

For descriptor operation code 1 or 2, the complete selected source path depends only on descriptor+0x20 bit 18. Four source branch ledgers cover the exact cases:

| Code | Bit 18 | Source behavior | Raw u32 result |
| --- | --- | --- | --- |
| 1 or 2 | Clear | `DSB SY` at `0xfffffe000c531c44`, then return | 0 |
| 1 or 2 | Set | Return before the barrier | `0xe00002d9` |

Neither path reads X2/X3, the supplied offset/length, or calls a range/mapper helper. This is the pinned implementation's selected behavior, not a claim about other operation codes or builds. The earlier hardware quantum caller still does not branch on either binding or cache-operation result before `_configureAES`; real API side effects cannot be replaced by the earlier no-effect fixtures merely because returned registers were ignored. No native barrier was executed. [DP1-DP4,DP7,DP8]

## Segment cursor, endpoint and transfer-count interfaces

`genIOVMSegments(D,cursor*,records*,count*)` shifts the three pointers to X4/X5/X6, takes the output callback from D+0x50, supplies an internal callback shim at `0xfffffe000c527590`, sets W1=`0x80` and tail-branches to the unnamed walker. Callback authentication is present in source and remains unexecuted. The walker requires a nonzero active count for flags `0x80`, nonnull pointers and a nonzero supplied u32 record count. A zero active count selects raw `0xe00002d8`; null pointers or zero supplied count select `0xe00002c2`. [DP2-DP4,DP7,DP8]

The initial range gate at `0xfffffe000c526e2c..0xfffffe000c526e44` computes, in modular u64 arithmetic:

```text
absolute = prepared_offset + *cursor
end      = prepared_offset + prepared_length
require absolute < end                 // unsigned
otherwise raw status = 0xe00002e8
```

At the selected prepared offset 0, this is exactly `*cursor < prepared_length` for every u64 value. For arbitrary nonzero offsets the same simplification requires both additions not to wrap; a SAT control disproves its unconditional use. This is an abstract coordinate-control result, not a native input example. [DP6]

The captured walker contains descriptor DMA-operation, mapping-table, callback, alignment and capacity branches beyond this initial gate. Its complete loop is not proved here. The end-clipping cut computes `segment_length + end - position`; it equals `end - segment_start`, positive and bounded by the original segment length, only under the retained nonwrapping interval premises. The successful output cut writes cursor=`position-prepared_offset` as u64 and count as u32. These local identities do not establish a valid mapper state or all callback/record invariants. [DP3,DP6,DP7]

The output shim shifts its payload to the callback ABI `(DMA,address64,length64,records,index)`. For u32 address-bit field D+0x5c in 1..63, it tests the modular inclusive endpoint `(address+length-1)>>bits`. A nonzero result selects candidate error `0xe00002e1` when R+0x7b is nonzero or the D+0x40 mapper pointer is NULL; otherwise the candidate status is zero. The callback is still invoked. A nonzero callback return preserves that candidate status; callback zero selects `0xe00002e1`. This source address-field policy is distinct from prepared logical coordinates and native bus acceptance. No nonwrapping physical-address theorem is asserted. [DP3,DP6,DP7]

The previously recovered `OutputLittle64` writes adjacent u64 address/length words and returns 1. Its exact record address is `records + zero_extend64((u32(index)<<4) mod 2^32)`. The new u64-domain source proof retains that 32-bit index arithmetic; actual record capacity and caller index bounds remain premises. This separates Boolean codec success from the shim's raw status result and the walker's cursor/count publication. [DP3,DP7]

At the separate hardware transfer consumer, original calls at `0xfffffe0009d5121c` and `0xfffffe0009d51260` request one record from each adapter. Returned records contain adjacent little-endian u64 address/length words. Source `0xfffffe0009d51268..0xfffffe0009d5127c` universally computes `min(remaining,length_A,length_B)`. This refines the earlier three finite minimum examples to a u64-domain identity and bound. No configuration-success continuation or register emitter executes. [DP7,DP8]

## Reproduction, validation and bounded continuation

Run the generator with `--verify`, followed by the publication auditor, using a Python environment that supplies Capstone, Z3 and `compression.zstd`. Portable invocation: `PYTHONPATH="triage_evidence${Z3_PYTHONPATH:+:$Z3_PYTHONPATH}" Z3_LIBRARY_PATH="$Z3_LIBRARY_DIR" "$PYTHON" -P triage_evidence/recover_aes_dma_preparation.py --verify`; replace the script with `triage_evidence/verify_aes_dma_preparation_publication.py` for the audit. No local interpreter/SDK path is embedded.

Forty-three UNSAT certificates cover 39 source cuts / 115 lifted instruction instances. One SAT premise control and four cache source paths are retained. The independent audit rechecks source bytes/bounds/symbols, nine original slots, branch and call ledgers, selected caller-state preservation, all new queries and the 29 frozen provider queries. It verifies original-input preservation, the exact manifest delta and path hygiene, including decoded archives and commit metadata. There is no native execution, runtime measurement, new Mach-port emission finding or IDB mutation.

Extraction and straight-line expression construction take O(B+I) time/space for collection bytes B and captured instructions I; manifest/hygiene checks take O(A) time for audited artifact bytes A. SMT cost is separate and each query has a 15 s observation limit. Byte counts and bit widths are exact integers; no timing or throughput is inferred.
