# IOKit user-client termination notifications

On macOS build `26C5035r`, an interest registration on an individual IOKit user-client registry entry can deliver a termination event that identifies the entry. Two native controls opened fresh `IOSurfaceRoot` connections and observed Mach message 53 after close. The descriptor in each event resolved to the same 64-bit registry entry ID found through its connection before close. Whether `fairplayd` registers for this event, and whether a particular FairPlay user client emits one, remain unknown. [Connection-to-registry join](live_iokit_port_description_report.md) [FairPlay connection retirement](live_fairplay_connection_retirement_report.md)

## Registration and delivery

All addresses are unslid. The registration transaction, synchronous close transaction and termination event use different Mach message IDs and port roles.

| Stage | Installed site | Port and data flow |
| --- | --- | --- |
| Send interest registration, request 2869 | IOKit `0x184ebf8e8`, MIG call at `0x184ebfa90` | The destination is the registry object right of the service being watched. Header uses COPY_SEND for that right and MAKE_SEND_ONCE for the thread's MIG reply right. The complex request contains one MAKE_SEND descriptor for the notification wake port, an interest name, and four u64 reference slots populated by the wrapper. |
| Accept registration and prepare reply 2969 | Routine slot `0xfffffe0007e784c0`, stub `0xfffffe000be80da4`, implementation call at `0xfffffe000be80f18`, object export at `0xfffffe000be80f60` | The stub resolves the registry right, validates the descriptor, interest name and reference extent, and passes the service, wake right and references into IOKit. On success the complex reply contains a send right to the `IOServiceMessageUserNotification` registration object. |
| Announce termination | `0xfffffe000c52188c` through `0xfffffe000c5218a0` | Calls the victim service's `messageClients` with type `0xe0000010` and the termination options. The source places this fanout before the `didTerminate` walk. |
| Build and send event 53 | Handler `0xfffffe000c5b13cc`, builder `0xfffffe000c5b1628`, send call `0xfffffe000c5b15b8` to `0xfffffe000bd3d6bc` | COPY_SEND destination is the registered wake port. The sender supplies a MOVE_SEND header right for the registration object and a MOVE_SEND descriptor for the service supplying the event. The builder writes 53 at `0xfffffe000c5b1670`. |
| Dispatch in the receiver | `0x184ec021c`, registration check at `0x184ec02ac`, callback at `0x184ec0364`, right cleanup at `0x184ec0374` and `0x184ec0398` | The dispatcher checks the send reference count of the incoming header's remote name. With that name present it requires a successful count of at least two before dispatching. Service-interest dispatch uses the descriptor's object name when present and otherwise uses the saved service name. The dispatcher releases the received registration and descriptor rights. |

The four outgoing u64 references are zero, callback, context and original service name. The installed stub permits up to eight u64s and checks the supplied message extent. XNU stores the wake right on the notification object and releases it when that object is freed. The receiving dispatcher can suppress a pending callback independently of whether the event reached the wake port. [LP64 registration signature](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/device/device.defs#L631-L637) [Registration implementation](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/iokit/Kernel/IOUserClient.cpp#L2990-L3092) [Registration lifetime and event sender](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/iokit/Kernel/IOUserClient.cpp#L1066-L1220) [Termination fanout](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/iokit/Kernel/IOService.cpp#L2819-L2845) [IOKit wrapper](https://github.com/apple-oss-distributions/IOKitUser/blob/323ead896d04424f87184d8f6ff0cce811aab106/IOKitLib.c#L750-L772) [IOKit dispatcher](https://github.com/apple-oss-distributions/IOKitUser/blob/323ead896d04424f87184d8f6ff0cce811aab106/IOKitLib.c#L1113-L1222)

## Native receipt layout

Each control opened its own IOSurface user client and registered for general interest on the child registry entry. Its 10 ms pre-close receive timed out with `0x10004003`. `IOServiceClose` returned success. The subsequent receive succeeded within its 1,000 ms bound. Those bounds are timeouts. The receipt contains no measured latency. The ordinary close transaction uses requests and replies 2816 and 2916. [FairPlay close and connection rights](live_fairplay_connection_report.md)

| Offset in received message (B) | Size (B) | Observed value or role |
| ---: | ---: | --- |
| 0 | 24 | Header bits `0x80001111`, size 124 B, remote name = registration, local name = wake port, voucher 0, ID 53. |
| 24 | 4 | Descriptor count 1. |
| 28 | 12 | Port descriptor with an exported name for the observed child, disposition 17 at offset 38 B and type 0 at offset 39 B. |
| 40 | 8 | Notification size field 76 B and type `0xa0`. The field is 64 B of maximum message argument plus 12 B of LP64 interest content. Actual extent comes from the Mach header. |
| 48 | 64 | Eight u64 reference slots. Slots 1 and 2 contain the callback and context and are zeroed in the receipt. Slot 3 contains the original child registry name. The other observed slots are zero. |
| 112 | 12 | u32 type `0xe0000010` (`kIOMessageServiceIsTerminated`) and u64 option word 1 at offset 116 B in these controls. |

The receipt extent is `24 + 4 + 12 + 8 + 64 + 12 = 124 B`. The old registry name returned `KERN_INVALID_NAME` after close. The descriptor supplied a different name that resolved to the same child ID with diagnostic type `0x1e`. With the registration retained, two send references were present after receive and the callback ran once with the descriptor name, type and option word. After dispatch the registration count returned to one. Releasing the registration after receive left one reference before dispatch, suppressed the callback and left the name invalid after dispatch. [XNU notification layout](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/iokit/IOKit/OSMessageNotification.h#L43-L103) [XNU event constants](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/iokit/IOKit/IOMessage.h#L39-L58)

## Assumption register and application to FairPlay

| Assumption | Dependent conclusion and impact | Falsification probe |
| --- | --- | --- |
| A1. The watched registry entry is the exact user client under study. | High. A matching descriptor ID can identify the retiring client. | Compare the pre-close connection description with the chosen child registry ID and the received descriptor. An interest registration on the parent or a different child tests a different object. Both native controls satisfied A1. |
| A2. The event and any proposed FairPlay method or close belong to the same client lifetime. | High. A join to a production FairPlay connection remains unknown. | Require a registry ID match and a consistent task generation, namespace and right lifetime across the records. A close reply and a nearby message 53 alone do not establish the join. |
| A3. The registration survives until userspace callback dispatch. | Medium. A callback trace can undercount messages actually received. | Compare the wake-port receive with the registration send reference count and dispatch outcome. Releasing the registration after receive falsified A3 in the second native control. |
| A4. Finalization is a separate lifecycle milestone. | Medium. Message 53 establishes return of a termination event for the identified entry. | Correlate finalizer or reference teardown evidence independently. The installed fanout precedes the source's `didTerminate` walk. |

The existing FairPlay lifecycle reports establish close and retirement paths. A FairPlay-specific interest link would require evidence for the registration call with the per-client registry right, or an observed descriptor tied to that object's ID. The control enumerates up to N provider children in O(N) time with O(1) additional matching state. Its two receives and layouts are verified independently of the static 54-instruction audit.
