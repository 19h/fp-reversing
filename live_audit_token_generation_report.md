# Installed task-token path and exec generation checks

On macOS build `26C5035r`, a controlled child retained its PID across `exec` while its kernel-issued audit token changed at word 7, the PID version. This happened both when the child re-executed the same image with the same CodeDirectory hash and when it switched to `/bin/cat`. In both cases `csops_audittoken` rejected the pre-exec token with `ESRCH` while the post-exec token succeeded for the same PID. Installed kernel instructions locate the two comparisons and their shared error branch before output. This establishes how the kernel qualifies the process identity used by the previously recovered CoreADI Security framework lookup. ## Task-name right and Mach message routing

The boot fileset digest is `0389ee48091668ef1f3f5bb9f85e1b020e442451f9321df695ba48e49cc64126`, with kernel UUID `90195379-954d-3ca3-baac-327341f14211`, matching the running kernel. The dispatch checks independently match the kernel tables, their parallel name entries and their executable consumers. The Mach table uses 24 B rows and its handler pointer is 8 B into each row. The BSD table uses the same stride with the pointer at row start. [Apple XNU Mach trap selector](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/syscall_sw.c#L138-L146) [Apple XNU syscall selector](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/syscalls.master#L255-L258)

## Token-qualified code-signing lookup

BSD rows `169` and `170` bind to `0xfffffe000c30e510` and `0xfffffe000c30f25c`. Both enter a shared implementation at `0xfffffe000c30e52c`. The plain call supplies a null token pointer. The qualified call loads the fifth argument at `+0x20` B in the kernel argument record, rejects a null pointer with `EINVAL`, and passes a present pointer to the shared implementation. The selected path finds the process by PID and copies in exactly 32 B at `0xfffffe000c30e6cc`. It reads the two token words from stack `+0x54` and `+0x5c`, relative to the token base at `+0x40`. The PID comparison at `0xfffffe000c30e6dc` and the version comparison at `0xfffffe000c30e6e8` both send mismatches to `0xfffffe000c30e738` with status 3 (`ESRCH`). The target version is from the read-only process object `+0x18`, consistent with the installed `proc_pidversion` accessor at `0xfffffe000c3081a4`. [Apple XNU token-qualified process comparison](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_proc.c#L3406-L3443)

The checks precede both the code-signing query policy and the opcode dispatch. The same dispatch table selects `CS_OPS_STATUS` at `0xfffffe000c30ea50` and the DER operation `16` at `0xfffffe000c30ed44`. The direct DER return path calls the entitlement getter at `0xfffffe000c30ed78` and the shared blob-output helper at `0xfffffe000c30ed98`. The native controls exercise `CS_OPS_STATUS` and `CS_OPS_CDHASH`. The installed ordering applies to DER as well, while the audit does not measure a post-exec DER lookup in a daemon. ## Native exec controls

The verifier held each of its two child processes at pipe markers before and after `exec`. The markers bracketed each identity read, including in the same-image case where a CDHash change could not mark the transition. The verifier released each task-name reference after the token read. Both children exited normally on pipe EOF. The two tokens' first seven words were identical in each case. The native process therefore stayed live and kept the same PID and credential words while its PID version changed. This agrees with the source reference's exec-time version update. [Apple XNU exec identity update](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_exec.c#L6629-L6645)

| Exec case | CDHash changed | Fresh token before exec | Old token after exec | Fresh token after exec |
| --- | --- | --- | --- | --- |
| Same Python executable | No | Both queries succeed | Both return `-1`, `errno = 3` | Both queries succeed |
| Python to `/bin/cat` | Yes | Both queries succeed | Both return `-1`, `errno = 3` | Both queries succeed |

Each failure left both the 4 B status buffer and 20 B CDHash buffer unchanged. Each successful value matched the independent plain `csops` result for the same live PID. The verifier independently matched the replacement `cat` CDHash against `codesign` for the installed `arm64e` slice. The receipt retains output widths, status and equality checks. The numeric task names, PIDs and token words stay out of the receipt.
